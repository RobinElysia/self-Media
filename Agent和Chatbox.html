From ChatBox to Agent

从聊天，到自主执行

理解 ChatBox、Agent、模型 API、框架、MCP、Skills，以及真正高效使用 Agent 的工程方法。

从“问模型”开始，最后走向“让模型参与完成任务”。
01 / 20
01 · ChatBox

什么是 ChatBox？

一个看起来只是聊天的界面，本质上是在管理人与模型之间的一段上下文。

01 · UI

聊天界面

用户输入问题，系统组织消息、历史记录、系统指令和附件，再把它们交给模型。

02 · ENGINEERING

上下文工程

决定模型此刻“知道什么”。消息顺序、历史、文件、检索结果都会改变它的判断空间。

ChatBox：主要目标是生成回答
02 / 20
02 · Context & Prompt

上下文工程 + Prompt 工程

Prompt
定义模型应该如何工作：角色、目标、约束、输出格式。
Context
提供模型当前需要知道的事实：历史、文件、工具结果、项目状态。
Memory
把值得跨轮次保留的信息，从临时对话中抽离出来。

Prompt 解决“怎么做”；Context 解决“依据什么做”。Agent 工程首先就是管理这两个东西。

03 / 20
03 · Agent

什么是 Agent？

一种能够调用模型 API，并围绕目标进行“观察 → 决策 → 操作 → 再观察”的应用系统。

OBSERVE读取当前状态
DECIDE决定下一步
ACT调用工具执行
VERIFY检查结果
Agent = Model + Context + Tools + Loop
04 / 20
04 · Model API

什么是“大模型厂商 API”？

你的程序Agent / ChatBox
API 请求鉴权 · 输入 · 工具定义
模型推理理解 · 生成 · Tool Call
返回结果文本 / JSON / 工具调用

API 是模型能力的“程序化入口”，不是 Agent 本身。真正的自主性来自你在 API 外围建立的执行循环。

代表性模型厂商：它们都在提供什么？

Responses / Agents

OpenAI 的 API 提供 Responses 等调用路径，并可挂接 web search、file search、function calling、MCP 等工具；2026 年还推出了基于 Codex harness 的 Agents API 公测。

ANTHROPIC

Messages + Tools

✦
GOOGLE

Gemini API

Gemini API 同时覆盖多模态、Function Calling、内置工具和超长上下文；官方把 Interactions 作为面向 agentic workflows 的推荐原语。

DS
DEEPSEEK

Tool Calls

阿里云百炼提供 Qwen 模型 API，同时提供 OpenAI-compatible 接口；Qwen 支持 Function Calling、多工具并行等能力。

06 / 20
06 · Same Idea, Different Interfaces

API 很像，但“接口哲学”并不完全一样

MODEL CALL

最基础：把输入交给模型，拿回文本或结构化输出。

TOOL CALL

模型返回一个函数 / 工具调用请求，由你的程序执行，再把结果送回模型。

AGENT RUNTIME

进一步把“多轮调用、状态、工具、上下文、停止条件”封装成更高层 runtime。

// 一个典型 Agent 请求
input → model → tool_call → tool result → model → final

不同厂商在 API 结构、工具定义、状态管理和内置工具上存在差异；做跨厂商 Agent 时，需要以具体 provider 文档为准。

07 / 20
07 · Autonomy

“自主探索和操作”到底怎么来的？

01 · GOAL

给目标，不给完整答案。

02 · STATE

暴露文件、环境和当前状态。

03 · TOOL

赋予搜索、Shell、代码等能力。

04 · LOOP

工具结果回流上下文，继续决策。

05 · STOP

完成、失败或触发边界后结束。

自主不是模型突然“有意识”，而是程序给了它连续行动的闭环。
08 / 20
08 · Framework

Agent Framework 是什么？

框架的价值，不是让模型变聪明，而是把 Agent 运行时里重复、复杂、容易出错的工程问题抽象掉。

LOW LEVEL

自己造 Loop

自己处理模型调用、工具 dispatch、状态、重试、终止条件和上下文。控制力最高，但工程成本也最高。

FRAMEWORK

复用 Agent Runtime

把模型、工具、memory、handoff、guardrail、workflow 等常见能力封装成可组合组件。

09 · Framework Landscape

常见 Agent 框架：定位不一样

LC
LANGCHAIN

通用 LLM / Agent 开发

提供模型、工具、Agent 与上层应用组件；适合快速搭建常见 Agent。

LG
LANGGRAPH

图式编排 / 状态机

更强调可控的状态、分支、持久化和长流程执行；适合需要精细编排的系统。

OA
OPENAI

Agents SDK

以少量核心原语构建 Agent，覆盖 tools、handoffs、guardrails、sessions、tracing 与 sandbox agents。

AG
AUTOGEN

多 Agent / Runtime

微软体系下的 Agent 框架，AgentChat 偏快速构建，多 Agent Core 偏事件驱动与可扩展 runtime。

CR
CREWAI

Crew + Flow

把自主协作团队与结构化、事件驱动的 Flow 组合起来，强调角色化 Agent 与工作流。

资料依据：LangChain / LangGraph / OpenAI Agents SDK / Microsoft AutoGen / CrewAI 官方文档。
10 / 20
10 · Framework Choice

选框架，本质是在选择“你想把控制权放在哪里”

HIGH ABSTRACTION

快速把一个任务变成可用 Agent。少写 runtime 代码，多利用框架默认行为。

CONTROL

自己定义状态、路由、重试、并发、checkpoint、human-in-loop 等细节。

DOMAIN

数据型应用偏 LlamaIndex；多 Agent 偏 AutoGen / CrewAI；OpenAI 体系则可以直接使用 Agents SDK。

因此没有一个“最好框架”适合所有 Agent；更重要的是先明确任务复杂度和控制要求。

LlamaIndex 也把 agents 与 workflows 结合，突出“在数据之上构建 Agent”的路径。

11 · Agent Products

有哪些 Agent？先看“谁家的”

O
OPENAI · CODEX

Codex

OpenAI 的 coding agent。CLI / 云端 / IDE 等形态都围绕“理解仓库 → 改代码 → 跑命令 → 验证结果”工作，并支持 Skills 与多 Agent 工作流。

C
ANTHROPIC · CLAUDE

Claude Code

Anthropic 的终端 coding agent。直接进入项目环境，读取与修改文件、执行命令，并支持 MCP、权限模式与长会话工作流。

✦
GOOGLE · GEMINI

Gemini CLI

Google 的开源终端 Agent。面向本地项目、文件操作、Shell、MCP 和 Skills，强调 terminal-first 的工作方式。

CU
ANYSHP · CURSOR

Cursor Agent

编辑器与 CLI 中的 Agent。可搜索代码库、编辑多文件、运行终端，并提供 Agent / Ask / Manual 等模式。

DV
COGNITION · DEVIN

Devin

Cognition 的 AI software engineer。面向复杂工程任务、迁移、PR review、on-call 与长期任务，并逐渐扩展到本地 CLI 与云端协作。

OH
OPEN SOURCE · OPENHANDS

OpenHands

开源的软件开发 Agent 方向，强调可执行的开发工作流，可围绕代码、工具与 workspace 运行。

这里的分类是“代表性产品”，不是能力排名。你原提纲中的 DSH 未找到足够明确的官方对应产品，因此没有擅自把它等同于某一个 Agent。

12 · Agent Anatomy

为什么这些产品看起来很像？

MODEL负责理解、推理、决定下一步
HARNESS负责规则、上下文、权限、状态
TOOLS负责读写文件、Shell、搜索、网络
WORKSPACE负责真正产生副作用的环境

真正决定 Agent 好不好用的，不只有模型本身，还有包在模型外面的 harness。

OpenAI 对 Codex 的工程文章把 harness 描述为协调 user、model 与 tools 的 agent loop；Cursor 也将 Agent 概括为 model + tools + harness。
13 / 20
13 · MCP

MCP：把外部能力接进 Agent

Agent负责选择下一步
MCP Server暴露工具 / 资源
External SystemGitHub · DB · SaaS · Search

它扩展什么？

能力边界。让 Agent 接触模型自身无法直接访问的外部数据或操作。

它带来什么成本？

系统耦合。接入越深，权限、认证、失败处理与安全边界就越需要工程化。

MCP 官方规范将其定义为连接 AI applications 与外部数据源、工具及工作流的开放协议。

14 · Skills

Skills：把知识和流程变成可复用资产

KNOWLEDGE

Markdown / Rules

把背景、规范、最佳实践、边界条件和判断标准写下来，让 Agent 可以在需要时读取。

PROCEDURE

Scripts / Workflow

把重复动作固化成脚本和操作流程，减少每次都从零解释怎么做。

Skill = Knowledge + Procedure + Optional Execution

所以 Skills 很适合做“知识蒸馏”：不是训练模型，而是把经过验证的方法压缩成 Agent 可复用的上下文。

15 / 20
15 · MCP vs Skills

一个偏“手”，一个偏“脑内操作手册”

MCP

接能力

把 GitHub、数据库、搜索、内部 SaaS 等外部系统接进 Agent。重点是“它能做什么”。

Skills

沉淀方法

把团队规范、流程、经验写给 Agent。重点是“它应该怎么做”。

两者可以同时存在：Skill 告诉 Agent 规则，MCP 给 Agent 工具。

16 · Codex Workflow

如何高效使用 Agent？先看 Codex CLI

# 进入项目
$ cd my-project

# 让 Agent 先理解任务，再执行
$ codex
› 请先检查这个仓库的结构，定位认证模块，
然后把 session 校验重构为 middleware，并运行相关测试。

# 完成一个阶段后，主动整理上下文
› /compact
✓ 保留：当前架构、已修改文件、测试结果、未完成任务

核心不是“多写 Prompt”，而是让 Agent 长时间工作时始终保持干净、可恢复、可验证的上下文。

Codex CLI 当前支持手动 /compact；OpenAI 官方文档同时介绍了 /init、/status、/permissions 等 CLI 工作方式。

17 · Context Compaction

/compact：不是删除记忆，而是重建工作状态

RAW

大量聊天、命令、文件和失败尝试。

SELECT

找出仍然影响下一步的事实。

SUMMARIZE

把过程压成高密度状态。

CONTINUE

以新的上下文继续任务。

VERIFY

检查 Agent 是否还记得关键约束。

长任务效率的关键：让 Context 与任务阶段同步变化
Codex 社区 issue / CLI 实现记录了 /compact 用于手动压缩会话上下文；具体行为可能随 CLI 版本演进。

18 · Project Entry + Sub-Agent

两个高级技巧：让 Agent 更像“项目成员”

01 · PROJECT ENTRY

初始化项目入口

用 AGENTS.md / rules / skills 写清技术栈、目录边界、验证方式、禁止事项和工作习惯，让 Agent 每次进入项目都有共同起点。

02 · SUB-AGENT

拆分专门代理

主 Agent 负责拆任务和汇总；Research、Coding、Review 等子代理各自拥有更窄的职责和上下文。

/init

在 Codex CLI 中初始化项目指令文件入口。

AGENTS.md

把项目长期约定从聊天记录中抽离出来。

Sub-Agent

减少单个上下文的复杂度，让不同角色并行或串行工作。

Codex 官方文档说明 CLI 会自动发现并注入 AGENTS.md；OpenAI Agents SDK 与 LangChain 等也都提供 handoff / subagent 等多 Agent 编排方式。

CHAT
